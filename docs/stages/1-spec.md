# 1. spec — 기획

요청을 받아 **무엇을 해결할지**와 **지금 어떻게 돼 있는지**를 `1-spec.md` 하나에 적습니다.
해결 방법은 다루지 않습니다 — `plan`의 일입니다.

에이전트 지시: [skills/spec/SKILL.md](../../skills/spec/SKILL.md)

## run 시작

run이 열려 있지 않으면 훅은 아무것도 막지 않습니다. run을 여는 길은 `/rein:spec <요청>` 하나뿐입니다.

1. `mcp__rein__status` — 이 세션에 열린 run이 있는지, 이어 갈 run이 있는지 봅니다.
2. `rein:slug` 에이전트가 요청을 보고 슬러그를 하나 만듭니다. 이것이 `runId`입니다.
3. `mcp__rein__open_run` — 훅이 형식·중복을 확인하고 run을 엽니다. 세션 루트 저장소에 쓸 수 있는 `.rein/config.json`이 없으면 거부하고, 세션은 `rein:setup`으로 config를 쓴 뒤 다시 엽니다.
   - run 폴더: `~/.rein/<project>/active/<runId>/`
   - 프로젝트 룰(`~/.rein/<project>/rules/*.md`)과 공용 룰(`~/.rein/rules/*.md`)을 이 시점에 동결합니다. run 도중 룰 파일이 바뀌어도 이 run에는 영향이 없습니다.
   - 공용 룰은 `rules:<이름>`으로 부르고, 세션 루트와 run이 고치는 바깥 저장소 모두에 적용합니다. `paths:` glob은 파일이 든 저장소 기준입니다.

한 세션은 run 하나만 쥡니다.

## 1-spec.md

[template.md](../../skills/spec/template.md) 형식을 따릅니다.

| 부분 | 내용 |
|---|---|
| front matter | `slug`, `유형`(`feature`·`bugfix`·`improvement` — 채점 기준이 갈림), `목표`(한 줄), `작성일`, `참조`(이슈 번호 또는 `없음` — land 커밋 제목에 들어감) |
| 문제 | 무엇이 왜 잘못됐는지. 요청에 따로 끝나거나 실패할 수 있는 결과물이 2개 이상이면, 첫 채점 전에 그 목록을 사용자에게 확인받아 `결과물 (사용자 확인, 날짜):` 아래 한 줄씩 적습니다. 자세히 말한 결과물이 짧게 말한 결과물을 가리지 않게 하려는 것입니다. 이번 run에서 빼기로 한 결과물은 `제외 (사용자, 날짜: 이유)`로 남깁니다. 채점자는 완료 판정이 `제외`가 아닌 결과물을 모두 다루는지 봅니다 |
| 전제 확인 | 요청의 주장을 코드로 확인한 결과. 버그면 실제로 일어나는지, 신규 화면·기능이면 이미 있는지(이름·기획서 절 번호·지식 `title:`로 검색). 요청이 가리키는 화면·열이 여러 곳에 맞거나 전달받은 요청이면, 분석 전에 요청자가 말하는 대상이 어디인지 먼저 묻습니다. 요청과 다르면 다른 질문보다 먼저 사용자에게 묻습니다 |
| 현행 동작 | 지금 동작과 관련 코드(`path:line`), 조사하며 찾은 경계 조건과 현재 처리 여부 |
| 완료 판정 | **한 줄**. 관찰 가능한 동작으로. qa는 이 줄만 봅니다 |
| 영향 범위 | 바꿀 코드에 기대는 것 — 호출자, API·스키마, 같은 테이블을 쓰는 쿼리, 설정 등. `- <path> — <무엇이 어떻게 기대는지>` 또는 `없음`. plan이 항목마다 답해야 합니다 |
| 범위 | 작업이 닿는 시스템 구성 요소 표. 행마다 `대상` 또는 `제외 (이유)`. 아래 「범위」 |
| 기획서 대조 | 기획서가 있을 때만. `원본:` 줄, 요구사항 한 줄씩 `포함`·`변경`·`제외`·`[?]` |
| 미해결 질문 | 있을 때만. 사용자가 「나중에」라고 했거나 「충분」으로 끝낼 때 남은 질문. 에이전트가 스스로 미루지 않습니다. 승인 화면에 목록이 나오고, plan이 질문마다 가정을 `2-plan.md`의 `## 결정 사항`에 적습니다 |

저장소 밖에서 사람이 손으로 적용할 파일(DB 스크립트 등)은 저장소 경로를 주지 않고 run의 `handoff/`에 둔다고 적습니다.

## 범위

화면 하나를 자세히 적은 요청은 그 화면이 함께 필요로 하는 API·배치·권한 설정을 가리기 쉽습니다.
`## 범위` 표가 구성 요소마다 대상인지 아닌지를 정해 두게 합니다.

- 플러그인 템플릿의 7행은 늘 있습니다: 화면·UI, API·엔드포인트, 데이터 스키마·마이그레이션, 배치·예약 작업, 권한·설정, 내보내기·보고서, 외부 연동.
- 도메인 지식에 범위 카탈로그 문서가 있으면 그 행을 아래에 더합니다(예: 화면마다 따라붙는 메뉴·권한 등록).
- 행마다 `대상` 또는 `제외 (이유)`, `근거`에 `path:line`이나 찾아본 곳. 코드로 정해지면 코드로, 요청이 열어 둔 곳은 `[?]`로 두고 사용자에게 묻습니다.

## 기획서 대조

요청에 기획서(PDF, 슬라이드, HTML, 화면 도면)가 있으면 그 요구사항을 `## 기획서 대조`에 한 줄씩 옮깁니다.
요약하지 않고 쪽 순서대로, 한 줄에 하나(컬럼 목록, 클릭 동작, 기본값, 버튼 위치, 규칙)를 적습니다.

| 상태 | 뜻 |
|---|---|
| `포함` | 기획서대로 |
| `변경: … (사용자, 날짜)` | 사용자가 바꿈 |
| `제외 (사용자, 날짜: 이유)` | 사용자가 뺌 |
| `[?] …` | 기획서가 비워 뒀거나 아직 안 정함 |

`변경`·`제외`는 사용자만 정합니다.

`rein:collator`가 대화를 보지 않고 `1-spec.md`와 `원본:`의 문서만 읽어, 줄이 없는 요구사항과 기획서와 다른 `포함` 줄을 답합니다.
`변경`·`제외`·`[?]` 줄은 지적하지 않습니다. 첫 `1-spec.md` 직후(as-is 그림·첫 채점 전)와, 그 뒤 `1-spec.md`가 바뀌었으면 advance 전에 돌립니다.
훅은 확인하지 않습니다.

## 그림 (`1-mockup.html`)

화면 배치가 바뀌거나 새 화면이 생기면 필수, 흐름·구조 변화는 도움이 될 때만 그립니다.
`rein:sketcher`가 `1-spec.md`와 코드만 보고 두 번 그립니다.

- **as-is** — 질문 전. 현재 화면에 `[?]`를 노란 메모로 표시
- **to-be** — 채점이 끝난 뒤. as-is 아래에 목표 화면, 미해결 질문은 빨간 메모
  - 요청에 기획서·도면이 있으면 표 열 수·항목 순서·클릭되는 칸이 `## 기획서 대조`에 있습니다. sketcher는 `원본:`의 화면 그림을 직접 열어 그 배치(영역, 순서, 차트·버튼의 위치와 크기 비율, 표의 열)를 기존 화면의 모양으로 그리고, 기존 화면과 다르면 파란 메모로 적습니다. `변경`·`제외` 줄이 그림보다 우선하고, `제외` 줄은 그리지 않습니다. 그림에서 그린 화면에는 `<!-- to-be source: brief/<파일> (<쪽>) -->`를 남깁니다.

### 기획서 그림과 배치 비교

to-be에 `to-be source`가 있으면 훅이 그 화면을 헤드리스 Chrome(없으면 Edge)으로 렌더링합니다(`hooks/render-mockup.js`, `agent/layout/mockup/<id>.png`).
메인 세션은 훅의 안내대로 `rein:layout-verifier`를 띄우고, verifier는 렌더링한 to-be와 기획서 그림만 보고 화면마다 `맞음`·`다름`을 `agent/layout-verify.md`에 씁니다. 기준은 배치이고, 색·글꼴·데이터는 보지 않습니다.

- `다름`이면 sketcher를 to-be로 다시 띄우고, 훅이 다른 곳을 sketcher에게 넘깁니다.
- 3번 연속 `다름`이면 sketcher는 렌더러가 잰 요소 위치·크기(`<id>.boxes.txt`)를 보고 원인을 한 문장으로 적은 뒤 고칩니다.
- 5번 연속 `다름`이면 훅이 다시 그리기를 멈추고, 승인 화면에 남은 차이를 알립니다.
- Chrome·Edge가 없어 렌더링하지 못하면 비교하지 않고, 승인 화면에 그렇게 적습니다.

그림은 요구사항을 더하지 않습니다. 지켜야 할 것은 완료 판정 줄에 적습니다.
to-be 화면은 plan의 `## 배치 대조`와 통합 qa의 배치 대조 칸으로 이어집니다.

## 채점과 질문

`rein:grader`가 `1-spec.md`만 읽고 `grade.md`를 씁니다. 대화는 보지 않습니다.

| 차원 | feature | bugfix | improvement | 채우는 쪽 |
|---|---|---|---|---|
| 문제 | 0.2 | 0.3 | 0.2 | 사용자에게 질문 |
| 완료 판정 | 0.3 | 0.25 | 0.25 | 사용자에게 질문 |
| 경계 조건 | 0.2 | 0.15 | 0.15 | 사용자에게 질문 |
| 현행 동작 | 0.1 | 0.2 | 0.2 | 코드를 읽고 채움 |
| 영향 범위 | 0.2 | 0.1 | 0.2 | 코드를 읽고 채움 |

- 가중치는 front matter `유형`으로 고릅니다. `유형`이 없으면 훅이 채점자를 띄우지 않습니다.
- 차원마다 0.2·0.6·1.0의 기준 문장(앵커)이 유형별로 있고, 채점자는 그 사이를 보간합니다. 문장은 `hooks/stages/spec.ts`의 `DIMENSIONS`에 있습니다.
- 모호도 = 1 − Σ(점수 × 가중치). **0.25 이하이고 하드 게이트가 없으면 통과.** 하드 게이트는 `## 범위` 표가 없거나, 템플릿 행이 빠졌거나, `대상`·`제외`가 아닌 행(`[?]`, `미확정`, 빈칸)이 있을 때입니다.
- 채점자는 점수마다 `1-spec.md` 문구를 그대로 인용해야 합니다. 훅이 원문에서 찾지 못하면 그 차원은 최대 0.4.
- 통과 못 하면 가장 약한 차원의 빈칸을 질문 **하나씩** 묻고, 답은 바로 `1-spec.md`에 씁니다. 질문은 코드가 아니라 화면을 아는 사람에게 쓰듯, 첫 문장에 지금 동작과 바뀔 점을 화면에 보이는 말로 적고 컬럼·테이블명은 뺍니다. 화면에 없는 말(상태 코드 `01`, 코드나 데이터의 용어)은 같은 문장에서 뜻을 풀어 씁니다. 화면에 보여도 사용자가 모를 수 있는 업무 용어(회계 용어 등)도 뜻과 작은 숫자 예를 붙입니다. 안마다 숫자나 행이 달라지면 실제 행 몇 개를 나란히 보여 줍니다. 기획서가 그리지 않은 상태(자료 없음, 조회 실패 등)의 화면 동작을 물을 때는 같은 앱 다른 화면의 방식을 먼저 찾아 `path:line`과 함께 안으로 보여 주고, 선례 없는 방식을 고르면 spec 줄에 `(선례 없음)`이라고 적습니다.
- 질문 첫 줄에 지금 채점 상태를 보여 줍니다. 예: `[완료 판정 0.4 · 모호도 0.42]`.
- 추천하는 안을 첫 선택지로 두고 이름 끝에 `(추천)`을 붙입니다. 「예」만 고르면 추천을 받아들이도록 묻습니다. 추천은 코드·기획서·다른 화면의 선례가 받칠 때만 하고, 무엇이 받치는지 설명에 적습니다.
- 채점 세 번 동안 모호도가 거의 그대로면(0.05 이하), 같은 질문을 돌고 있는 것입니다. 각도를 바꿉니다. 각각 run마다 한 번씩만 씁니다.
  - **반대로**: 빈칸 밑의 가정을 묻습니다. 그 조건이 없어도 답이 같은지.
  - **최소로**: 그래도 쓸모 있는 가장 작은 결과가 무엇인지 묻습니다. 사용자가 줄이면 완료 판정을 고치고, 미루겠다고 한 것만 미해결 질문으로 옮깁니다.
  - **본체로**: 답마다 같은 것을 부르는 말이 바뀌면, 요청이 가리키는 화면·값·기록 하나가 무엇인지 먼저 묻습니다.
- 사용자가 답 대신 되물으면(뜻, 지금 동작, 기획서 내용, 다른 화면의 방식, 쉬운 설명 요청) 답으로 적지 않습니다. 필요하면 조사해 텍스트로 먼저 답하고, 같은 질문을 고쳐 다시 적은 뒤 턴을 멈춥니다. 다음 메시지가 그 질문의 답입니다. 쉬운 말을 청하면 그 뒤 질문도 계속 그렇게 씁니다.
- 질문 3개마다 다시 채점해야 합니다. 질문 수 전체에는 상한이 없습니다.
- 사용자가 "충분"이라 하면 통과 못 해도 끝냅니다. 남은 빈칸은 미해결 질문으로 옮기고, 남은 모호도와 함께 승인 화면에 표시됩니다.

## 끝 — 사람 승인

`mcp__rein__advance`(답 없이) 호출 시 훅이 확인합니다.

- 완료 판정 줄, `참조:`, 영향 범위가 있는지
- 마지막 채점이 지금의 `1-spec.md`에 대한 것인지

통과하면 run은 사용자를 기다립니다. 사용자가 **`/rein:plan`**을 입력하면 승인입니다.
새 세션에서는 `/rein:plan <slug>`로 이어 갑니다. 에이전트가 스스로 승인할 수 없습니다.

승인된 `1-spec.md`는 동결됩니다. 나중에 바뀌면 훅이 알리고, `goto spec`으로 다시 승인받습니다.

## 모든 단계 공통 도구

| 도구 | 하는 일 |
|---|---|
| `status` | run의 단계·파일·멈춤 사유를 보여 줌. 읽기만 함 |
| `advance` | 다음 단계로. 사람 결정이 필요한 곳(관문)에서는 답 없이 부르면 선택지만 알려 줌 |
| `goto` | 아무 단계로 이동(예: plan으로 되돌림, 증거 그대로 land로). 커밋은 여전히 승인 필요 |
| `park` | `보류`(나중에 이어 감) / `폐기` / `완료 (Rein 밖에서 반영함)` |
| `resume` | 보류됐거나 다른 세션에 남은 run을 이 세션으로 가져옴 |

보류된 run은 `~/.rein/<project>/defer/`, 끝난 run은 `complete/`로 폴더가 옮겨집니다.
