# 4. review — 리뷰

바뀐 코드를 읽기만 하고 판정합니다. 아무것도 실행하지 않습니다 — 빌드·테스트는 qa의 일입니다.
코드를 쓴 세션이 채점하지 않도록, 판정은 `rein:reviewer`만 합니다. `review.md`는 그 에이전트만 쓸 수 있습니다.

에이전트 지시: [skills/review/SKILL.md](../../skills/review/SKILL.md) · [agents/reviewer.md](../../agents/reviewer.md)

## 입력

훅이 기록에서 만들어 reviewer의 프롬프트를 통째로 씁니다.

- **바뀐 파일** — dev 동안 훅이 기록한 쓰기 (`git diff`가 아님. 새 파일도 포함)
- **적용 룰** — 동결된 룰 중 `paths:` glob이 바뀐 파일에 맞는 것. `paths:`가 없는 룰은 항상 적용
- **설계** — `2-plan.md`의 `## 상세 설계`
- **지난 시도 기록** — `agent/fails.md`(회차별 읽은 실패). 실패일 때 구현·설계를 가리는 근거

## review.md

```markdown
## 설계 대조
판정: 통과 | 실패

## 룰 체크
- `api.md` — 판정: 통과        (룰마다 한 줄, 없으면 "적용 대상 없음")

## 정확성
판정: 통과 | 실패

## 변경 전 실패                 (2-plan.md에 있을 때만)
- <테스트 파일> — <케이스>: <변경 전 path:line>이 <옛 결과>를 내므로 단언이 실패

## 실패 원인                     (판정이 실패일 때만)
원인: 구현 | 설계
<이유>
```

| 섹션 | 보는 것 |
|---|---|
| 설계 대조 | 변경이 상세 설계를 따르는지. `## 변경 전 실패`의 단언마다 그것을 하는 테스트가 있고, 변경 전 코드에서 실제로 실패하는지 |
| 룰 체크 | 적용 룰을 지키는지. 설계와 룰이 충돌해도 `실패`. 공통을 먼저 쓰라는 룰이 있으면 바뀐 코드의 새 정의(함수·헬퍼·CSS 클래스·SQL 문자열 등)를 도메인 지식과 저장소에서 찾아 같은 일을 하는 공통이 있는지 보고, 찾은 범위를 적음 (`## 결정 사항`에 사용자가 고른 기록이 있으면 통과) |
| 정확성 | 추가·변경된 코드의 버그·보안 문제. 호출자부터 `path:line`으로 추적되는 것만. 가정·취향은 제외 |

spec의 완료 판정은 여기서 보지 않습니다 — 통합 qa의 일입니다.

## 나눈 리뷰

바뀐 파일이 10개 이상이면 reviewer 하나가 읽기에 너무 커서 나눕니다. 한 run의 reviewer가 2-plan.md와 diff를 합쳐 컨텍스트 43만 토큰까지 쓴 일이 있습니다(2026-11-03, 바뀐 파일 122개).

1. `rein:review-splitter`가 설계의 `###` 제목·`## 영향 범위`·`git diff --stat`·Grep만 보고, reviewer가 함께 읽어야 판정할 수 있는 파일끼리(호출하는 쪽과 불리는 쪽, 화면과 그 뒤의 서버 코드, 같은 키·컬럼을 바꾸는 파일, 테스트와 대상) 묶어 `review-groups.md`를 씁니다. 훅은 바뀐 파일과 handoff 파일이 모두 정확히 한 묶음에 드는지 검사합니다.
2. 묶음마다 `rein:reviewer`를 동시에 띄웁니다(프롬프트 `묶음 <n>`). 훅이 쓴 task에는 그 묶음의 파일, 각 파일의 설계 항목이 2-plan.md 몇 번째 줄인지, 그 파일에 걸리는 룰, 그 묶음 테스트의 `## 변경 전 실패` 줄만 들어갑니다. 각자 `review-<n>.md`를 `review.md`와 같은 형식으로 씁니다.
3. 모든 묶음의 판정이 모이면 한 번의 review처럼 옮깁니다. 하나라도 실패면 훅이 실패한 묶음의 내용으로 `review.md`를 씁니다. 실패한 묶음 중 하나라도 원인이 `설계`면 plan으로, 아니면 dev로 넘깁니다.

묶음 사이에 걸친 문제는 묶음 구성으로만 막습니다 — 따로 보는 reviewer는 없습니다.

dev를 다녀온 재리뷰는 실패한 묶음과, 통과했지만 그 뒤 파일이 바뀐 묶음만 다시 봅니다(dev가 끝날 때 봉인한 해시로 판단). plan을 다시 통과해 온 재리뷰도 같습니다. 어느 묶음에도 없는 새 파일이 생겼으면 묶음을 버리고 splitter부터 다시 합니다. 다시 볼 묶음이 하나도 없으면(모든 묶음이 통과한 뒤 바뀐 파일이 없음) 모든 묶음을 다시 봅니다. `goto`로 옮기면 묶음은 사라집니다.

## 결과

훅이 `review.md`가 써지는 즉시 형식과 판정을 읽고 run을 옮깁니다. 훅이 보는 형식은 세 절, `## 설계 대조`·`## 정확성`의 `판정:` 한 줄, 실패일 때의 `원인:` 줄입니다. `## 룰 체크`는 `판정 실패`가 든 줄이 있는지만 봅니다. 룰마다 한 줄인지, 줄 모양이 맞는지는 reviewer 지시일 뿐 훅이 거부하지 않습니다.

| 결과 | 다음 |
|---|---|
| 전부 통과 | `qa` |
| 실패, 원인 구현 | `dev` (worker가 `review.md`를 읽고 고침) |
| 실패, 원인 설계 | `plan` |
| 구현 실패가 반복돼 훅이 멈춤 | `review`에 머묾(`failure-route`). 메인 세션이 dev·plan을 고름 |
| 형식 불량(실패인데 원인 줄이 없거나 잘못됨 포함) | `review`에 머묾. reviewer 재실행 |

review 뒤에 메인 세션이 설계 파일을 고치면 훅이 알리기만 합니다. 다시 리뷰받으려면 `goto review`.
