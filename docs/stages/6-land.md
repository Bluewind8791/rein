# 6. land — 후처리

끝난 작업을 저장소마다 커밋 하나로 남깁니다. 커밋 메시지는 `6-land.md`에 씁니다. PR·push는 하지 않습니다.

- **워크트리 run** — 사용자가 한 번 승인하면 Rein이 워크트리에서 커밋하고, 그 커밋을 메인 작업 트리의 브랜치로 가져온 뒤 워크트리를 지웁니다.
- **워크트리 없이 열린 run**(워크트리 도입 전에 열림) — 스테이징까지만 하고, **커밋은 사용자가 직접 합니다.** Rein은 커밋하지 않고 묻지도 않습니다.

에이전트 지시: [skills/land/SKILL.md](../../skills/land/SKILL.md) · [skills/retro/SKILL.md](../../skills/retro/SKILL.md)

## 들어오는 길

- 통합 qa 통과 → 훅이 land로 옮김
- 사용자가 체크리스트를 직접 테스트하고 `/rein:land` 입력 → 훅이 모든 칸이 체크됐는지 확인

## 워크트리 run의 흐름

run은 처음부터 자기 워크트리(`<저장소>/.claude/worktrees/<slug>`, 브랜치 `rein/<slug>`)에서 작업했습니다. 그래서 메인 작업 트리 파일은 건드리지 않았고, 사용자가 같은 트리에서 병행하던 변경이 섞이지 않습니다. 워크트리를 언제 어떻게 만드는지는 [overview.md](../overview.md#워크트리)에 있습니다.

0. **메인 작업 트리로 돌아가기** — land는 메인 작업 트리에서 합니다. 세션이 워크트리 안에 있으면 먼저 `ExitWorktree`(keep)로 나옵니다. Windows에서는 세션이 잡고 있는 폴더를 지울 수 없어서, 나오기 전에는 `advance`가 거부합니다(`park`의 `폐기`도 같음).
1. **`6-land.md`** — 메인 세션이 커밋 메시지와 저장소마다 커밋할 파일 목록을 씁니다. 화면 문서를 갱신할 run이면 갱신본도 씁니다(「화면 문서」).
2. **`advance`(답 없이)** — 훅이 메시지가 있는지, 메인 작업 트리가 run을 시작한 브랜치에 있는지 확인하고 승인받을 내용을 돌려줍니다.
   - 저장소마다 넣을 브랜치와 커밋할 파일(계획 파일 중 바뀐 것)
   - 커밋하지 않고 워크트리와 함께 지워질 파일(계획 밖 변경, 예: 임시 파일). gitignore된 파일은 목록에 없고 함께 지워집니다.
   - 화면 문서마다 더해지는 줄(`+`)과 빠지는 줄(`-`). 새 문서면 `(새 문서)`
3. 메인 세션이 사용자에게 묻고, 답(`커밋` 또는 `취소`)을 `advance`에 넘깁니다.
4. **`커밋`이면** 저장소마다 훅이 차례로 실행합니다. 저장소의 git hook(pre-commit 등)은 끈 채로 돌립니다. 검증은 qa가 이미 했습니다.
   1. 워크트리에서 그 파일만 이름으로 `git add -A --` 한 뒤 커밋
   2. 메인 작업 트리에서 `git cherry-pick`
   3. `git worktree remove --force`, `git branch -D rein/<slug>`
5. 다 들어가면 run이 닫히고 폴더가 `complete/`로 옮겨집니다. 화면 문서 갱신본은 `~/.rein/<project>/requirements/`로 복사됩니다. 다른 프로그램(편집기, 띄워 둔 서버 등)이 워크트리 폴더를 잡고 있으면, git은 파일을 지우고 등록을 풀지만 빈 폴더가 남습니다. 그 경우 무엇이 남았는지 사용자에게 알립니다.

### 멈추는 경우

멈추면 메인 작업 트리는 원래대로이고, 워크트리와 커밋은 남습니다. 사용자가 정리한 뒤 `advance`를 다시 부르면 다시 묻습니다. 이미 만든 커밋은 다시 만들지 않고, 이미 들어간 저장소는 건너뜁니다.

- 메인 작업 트리가 run을 시작한 브랜치가 아닌 다른 브랜치에 있음
- cherry-pick 실패 → `cherry-pick --abort`로 되돌림. 메인 작업 트리에 **스테이징된 변경이 하나라도 있거나**, 같은 파일의 커밋 안 된 변경이 있으면 git이 거부합니다. 다른 파일의 unstaged 변경은 괜찮습니다.
- run을 시작할 때 detached HEAD였던 경우: 메인 작업 트리가 지금 있는 브랜치에 넣습니다. 여전히 detached면 멈추고 브랜치로 전환하라고 안내합니다.
- 커밋 서명(`commit.gpgsign`)을 켠 저장소: 훅은 저장소 설정에 적힌 프로그램이 실행되지 않게 `gpg.program`을 막고 git을 돌리므로, 커밋이 실패하고 git의 오류를 보여 줍니다. 서명이 필요한 저장소라면 Rein 밖에서 커밋하고 `park`의 `완료`로 닫습니다.

## 워크트리 없이 열린 run의 흐름

1. **스테이징** — 메인 세션이 계획된 파일 중 `git status`에 바뀐 것으로 나온 것만 이름으로 `git add`.
2. **`6-land.md`** — 메인 세션이 커밋 메시지와 저장소마다 스테이징 목록을 씀. 사용자가 읽고 커밋할 때 쓰는 문서입니다. 화면 문서 갱신본도 씁니다(묻지는 않음).
3. **`advance`** — 훅이 확인합니다.
   - `6-land.md`가 있음
   - 스테이징 = 정확히 "계획된 파일 중 바뀐 것"
4. 통과하면 run이 닫히고 폴더가 `complete/`로 옮겨집니다. 화면 문서 갱신본은 `~/.rein/<project>/requirements/`로 복사됩니다. 메인 세션이 사용자에게 `6-land.md` 경로를 알리고, 넘길 파일(`handoff/`)이 있으면 적용 방법도 알립니다.
5. 사용자가 그 메시지로 직접 커밋합니다.

## 화면 문서

화면마다 land된 요구사항을 모아 두는 문서입니다(이슈 #4). 같은 화면을 다시 고치는 run이 spec에서 지난 결정을 읽습니다.

- 위치: `~/.rein/<project>/requirements/<도메인>/<화면 id>.md`. 허브 카탈로그의 `<도메인>/requirements/`와 주고받습니다([distribution.md](../distribution.md)). 받은 도메인이 없는 프로젝트는 `requirements/<화면 id>.md`에 두고 이 PC에만 남깁니다.
- 형식: front matter(`화면`, `이름`, `갱신: <날짜> (run <runId>)`)와 표 `| 요소 | 요구사항 | 상태 | 근거 | run |`. 요소는 목업의 `data-id`, 화면 전체의 규칙은 `-`. 상태는 `구현됨`·`보류`·`폐기`. run은 그 줄을 마지막으로 바꾼 run입니다.

land에서 메인 세션이 `1-spec.md`의 `## 요구사항` 가운데 요소가 붙은 줄로 갱신본을 `agent/requirements/<도메인>/<화면 id>.md`에 씁니다. `mcp__rein__status`가 지금 문서, 갱신본을 쓸 곳, 프로젝트의 도메인을 보여 줍니다. 도메인이 여럿이고 새 문서면 사용자에게 어느 도메인인지 묻습니다.

| spec 줄 | 상태 | 근거에 더함 |
|---|---|---|
| `포함` | `구현됨` | 출처(기획서 쪽, `요청`, `사용자 코멘트`) |
| `변경` | `구현됨` | `→ 사용자 변경 <날짜>` |
| `보류` | `보류` | `→ 사용자: <이유> <날짜>` |
| `제외` | `폐기` | `→ 사용자 제외 <날짜>: <이유>` |
| land까지 남은 `[?]` | `구현됨` | `가정 (plan)` |

- 같은 요소의 기존 줄을 덮어쓸지 새 줄로 더할지는 메인 세션이 판단합니다. 워크트리 run은 바뀐 줄이 승인 화면에 나오므로 사용자가 확인합니다.
- 줄은 지우지 않습니다. 뺀 요구사항도 `폐기`로 남습니다.
- run이 닫히면 훅이 갱신본을 `~/.rein/<project>/requirements/`로 복사하고, 로컬 frame 서버가 허브로 보냅니다. run 폴더의 갱신본은 그 run이 land한 기록으로 남습니다. 취소하면 아무것도 바뀌지 않습니다.
- `## 화면`이 없는 run(배치·API만 바꾸는 run)의 요구사항은 화면 문서로 옮기지 않고 run 폴더에만 남습니다.
- 문서가 아직 없는 화면을 지난 완료 run이 다뤘으면, `mcp__rein__status`가 그 run들의 `1-spec.md`를 보여 줍니다. 메인 세션은 그 run들의 줄과 이번 run의 줄로 첫 문서를 씁니다. 지난 run의 줄에는 요소가 없으므로, 그 run 폴더의 `1-mockup.html`에서 `data-id`를 찾아 붙이고, 요소를 알 수 없는 줄은 뺍니다. 승인 화면에는 「새 문서」로 보입니다.

### 프레임의 화면 페이지

프레임 왼쪽 아이콘 막대의 「화면」으로 엽니다(`#~screens`). 로컬 프레임은 `~/.rein/<project>/requirements/`를, 허브 페이지는 카탈로그의 `<도메인>/requirements/`를 읽습니다.

- **왼쪽 화면 목록** — 도메인별로 묶고, 화면마다 줄 수와 run 수를 보여 줍니다. 문서가 없어도 진행 중이거나 완료한 run이 `## 화면`에 적은 화면은 「문서 없음」으로 「도메인 모름」 묶음에 올립니다. 로컬은 프로젝트별 화면이고, 프로젝트가 둘 이상이면 프로젝트 이름을 붙입니다. 허브는 화면 id 하나가 한 화면이고, 모든 프로젝트의 run을 셉니다.
- **가운데 요구사항 표** — 요소·요구사항·상태·근거·run. 상태(`구현됨`·`보류`·`폐기`)로 거릅니다. 줄을 펼치면 근거를 `→` 단위로 한 줄씩, 끝에 land한 run을 보여 주고, 그 아래 이 요소를 다룬 run들의 `## 요구사항` 줄(상태와 `원본:`)을 최근 것부터 보여 줍니다. 요소 태그가 없는 예전 run(0.72.0 이전)은 빠졌다고 한 줄로 알립니다.
- **오른쪽 run 목록** — 이 화면을 `## 화면`에 적은 진행 중 run과 완료 run을, 진행 중 run부터 최근 순으로 보여 줍니다. 보류·버림 run은 넣지 않습니다. 누르면 그 run으로 갑니다.

## 커밋 메시지

프로젝트 룰이나 저장소 문서에 커밋 규칙이 있으면 그것을 따릅니다. 없으면 기본 형식입니다.

```
[<참조>] <변경 요약>

<왜 바꿨는지>

<변경 전 동작. 변경 후 동작.>
```

`<참조>`는 `1-spec.md`의 `참조:` 값입니다. `없음`이면 대괄호째 뺍니다.

## 메인 세션이 커밋할 때

사용자가 시켜서 메인 세션이 `git commit`을 하면, 사용자 승인(`커밋`) 전에는 거부됩니다.
Rein 밖에서 이미 커밋했다면 `park`로 `완료 (Rein 밖에서 반영함)`를 골라 run을 닫습니다.

## 회고 (retro)

run이 닫히면(land 통과, 커밋할 것 없이 종료, `폐기`·`완료`로 park) `rein:retro`가 run 폴더와 세션 기록을 읽습니다.
배운 것을 종류에 따라 다르게 처리하고, 모두 `agent/retro.md`에 기록합니다.

- 도메인 지식: `rein:retro`가 `~/.rein/<project>/knowledge/<domain>/`에 바로 넣고, 메인 세션이 `catalog push`로 허브에 보냅니다. 사용자는 고르지 않고, 무엇을 넣었는지 보고만 받습니다.
- 하네스: 무슨 일이 있었고 무엇이 헛돌았는지(`문제:`)만 적습니다. 고칠 방법은 적지 않습니다.
- 도메인 룰: 룰(`제안:`)과 넣을 곳(`대상:`)을 적습니다.

사용자는 하네스와 도메인 룰 후보 가운데 고칠 가치가 있는 것을 고릅니다.
고른 후보는 Rein 저장소의 `learn` 스킬이 나중에 처리합니다. 하네스 후보는 그때의 코드를 읽고 고칠 방법을 정해 적용합니다.
